第五阶段：AI 技术方案与系统架构设计（v0.1 草案）

文档性质：技术方案规划，非已完成代码。标注 [现状] / [规划]。 约束先行（决定一切选型）：无 GPU（CPU 推理）· C 盘紧张（一切装 D 盘）· 照片不出本机（全 localhost，0 外部请求）· 用户非科班（用 AI 辅助编程生成脚手架，但架构/选型/PRD 由本人定）。

0. 设计原则

  1. 隐私优先即产品原则：全链路 localhost，浏览器 Network 面板须呈现 0 外部请求。这既是技术约束，也是面向文保/规划用户的卖点。
  2. 不为了 Agent / RAG 而堆技术：MVP 用「确定性工作流 + 关键步骤 LLM-in-the-loop」，RAG 检索增强留 P2。
  3. 规模匹配：构件约 59 条，检索用 numpy 余弦即可，不引重型向量库（避免过度工程）。
  4. 可演示、可复现：本地一键启动脚本（复用现有 start_vlm_workbench.bat 思路）。

3. 各层设计

3.1 前端改调（根治 CORS）

  • 现状：file:// 直连 Ollama，靠「父窗口直连」绕过 Origin:null 的 403。
  • 新方案：前端只调 http://localhost:8000/api/*；后端服务端调 Ollama。CORS 彻底消失，前端不再关心模型细节。
  • 建议：后端同时以静态路由托管 index.html，用户直接开 http://localhost:8000——既解决 file:// 怪异行为，又统一入口。

3.2 后端框架（FastAPI）

  • 为什么 FastAPI：① 原生 async，适合「Agent 分步跑 + SSE 推进度条」；② 自动生成 /docs OpenAPI，作品集可截图证明你懂接口契约；③ 与 Ollama 的 OpenAI 兼容 client 无缝对接。
  • 关键端点（草案）：
  • POST /api/upload 批量导入 + EXIF 转正
  • POST /api/rectify 四点透视校正（自动/手动）
  • POST /api/prelabel 调 VLM 出构件草稿框
  • POST /api/review 人工复核结果回写
  • POST /api/infer 知识约束层打分 → 候选风格 + 证据链
  • GET /api/atlas 构件图谱参考面板数据
  • POST /api/export 导出 CSV/JSON（0/1 矩阵 + 谱系）
  • GET /api/agent/run SSE 流式：编排整条流水线并推每步状态

3.3 VLM 调用层（本地 Ollama）

  • 模型：qwen3-vl:4b（已装 D 盘），经 OpenAI 兼容端点 http://localhost:11434/v1 调用。
  • 复用已踩坑经验（这是你真实亮点，写进作品集）：
  • thinking 死循环 → 关闭 think 或设超时熔断（单张超时则标「草稿失败，请人工」）；
  • 坐标不可靠 → 仅作橙色虚线草稿，不自动落库，强制人工确认；
  • 四层容错解析（沿用 vlm_prelabel.py）——把非结构化输出稳稳转成构件列表。
  • 性能预期（需实测）：CPU 上单张推理可能 10–60s；MVP 串行处理 + 进度条，演示用 5–10 张即可。

3.4 知识约束层（符号/规则层，非训练模型）[现状]

  • 数据：59 构件词表 + 5 类加权 infer() 逻辑（工作台已有），迁为后端 knowledge.py 模块。
  • 角色：VLM 草稿 → 约束层校验/打分 → 候选风格 + 证据链（每条构件列出加多少分）。这是「把领域知识作为 AI 的约束层」的产品化落地。
  • 与 RAG 关系：约束层是确定性规则；RAG 是检索增强（P2）。两者可并存——规则保证下限，检索提升上限。

3.5 构件图谱数据层 + RAG（P1 参考面板 / P2 检索增强）

  • 数据结构：atlas = [{id, name, images[], features, discriminative_notes, label}]
  • P1（MVP 先做）：后端 serve atlas.json + 图片，前端做「参考面板」——点构件看示例图 + 判别特征 + 易混点。独立就有用户价值，无需检索。
  • P2（RAG）：用 nomic-embed-text（Ollama，CPU）对 features 文本向量化；标注时对当前区域描述做检索，把最相关参考注入 VLM prompt → 降幻觉。
  • 诚实提醒：59 条规模做「向量库」是杀鸡用牛刀，numpy 余弦相似度即可；若图谱扩张到上千条再上 Chroma/FAISS。这体现 PM 的克制。

3.6 Agent 编排层（诚实定义「Agent」）

  • 关键澄清：这里的 Agent = 确定性工作流编排 + 关键步骤 LLM-in-the-loop，不是完全自主的 tool-use ReAct。原因：本地无 GPU、需可演示可复现、避免不可控。
  • 实现：后端用异步状态机串起 导入→校正→预标注→复核→推理→导出；每步产出状态事件，SSE 推前端进度条（对应 P1「Agent 进度可视化」）。
  • P2 可选增强：用 VLM 二次确认「争议/混合类型」，做语义仲裁。

3.7 隐私部署

  • 后端 bind 127.0.0.1；Ollama 本机；0 外部网络调用。
  • 验证：浏览器 Network 面板 0 外部请求（作品集可演示证明）。
  • 持久化：localStorage（会话态）+ 本地 JSON/CSV 导出（不传云）。

4. MVP 最小技术栈（落地清单）

  • 后端：Python venv（D 盘）+ FastAPI + uvicorn + openai（指向本地）+ Pillow
  • VLM：Ollama qwen3-vl:4b
  • 知识/图谱：JSON 文件
  • 前端：现有 index.html 改造，改调 localhost 后端
  • 检索：MVP 固定 few-shot；P2 再上 embedding
  • 不引入：数据库服务、GPU、任何云服务

一键启动：提供 start_agent.bat（激活 D 盘 venv → 启 Ollama → 启 FastAPI → 打开 localhost），复用现有 start_vlm_workbench.bat 思路。
