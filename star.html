0. 四个必须先想清楚的判断

  1. 「结果」不等于「效率提升 X%」。工程可用性结果（自检通过率、导入成功率、模型可用率）、数据处理规模（980→618→50）、AI 效果从 0 到可用，全部是合格且可验证的 R。你已经有 R 了，不需要等 v0.6。
  2. 你最值钱的不是「做了个工作台」，是三次产品判断：① 把风格判定权留在人手里（模型只认构件）；② 发现 VLM 不可复现后，不硬吹模型、改设计 human-in-the-loop 草稿隔离；③ 发现 618 张「可用」判宽了，把 50 张自动矫正全部标「待定」。这是成熟 PM 才会做的取舍，比任何功能列表都亮。
  3. 项目名与角色：沿用已确认的「骑楼志 · AI 遗产调研助手（HeritageLens）」。角色写「项目负责人 / 产品设计与 AI 方案」最稳；若目标岗明确写 AI 产品经理，可写「AI 产品经理（课程项目）」——两者都不虚，因为需求定义、方案选型、验收标准确实由你定。
  4. 【v0.2 新增】「模型识别不到位」不是减分项，是加分项。面试官不担心你选错过模型，只担心你不知道为什么错、也不知道下一步怎么判断。而且这个发现恰好强化了原来的产品判断：正因为通用小模型啃不动 59 个细粒度构件语义，才需要「领域知识约束 + 人工兜底 + 数据飞轮」。所以换模型不是推翻原方案，而是给原判断补一组对照证据。详见 §7。

1. STAR 拆解（用于面试口述，不是简历原文）

S · Situation（情境）

建筑学课题组承担台山华侨圩镇骑楼立面要素识别与类型谱系研究，方法对标 Xue et al. (2026) Nature Communications。田野调研积累约 1500 张照片，但有效样本需先清洗；构件标注与风格判断高度依赖资深研究者，学生难以上手；通用 AI（GPT/豆包类）不懂建筑构件语义、答案常幻觉且照片需上传云端，与文保/规划场景的数据合规冲突。运行环境还有硬约束：无 GPU、C 盘紧张、导师需双击即用。

T · Task（任务）

把一条断裂的研究链路（清洗 → 校正 → 标注 → 推理 → 谱系导出）重构成一个可被非专家使用、AI 输出可信任、数据不出本机的端到端产品，并在课程周期内完成可演示交付。个人承担：需求定义、用户场景拆解、竞品对比、PRD 与 P0/P1/P2 规划、AI 技术选型、验收标准制定、效果测试设计；代码实现借助 AI 辅助编程工具完成。

A · Action（动作，五条主线）

主线做了什么体现的 PM 能力
A1 需求与方案定义拆解三类用户（研究者/志愿者/规划调研员）与 5 大痛点；明确垂直领域差异化；定义「清洗→校正→VLM 预标注→人工复核→可解释推理→导出」单入口工作流；产出 PRD、用户故事、MVP 边界（P0 全链路 + 1 个 P1），主动把 RAG、模型训练、移动端延后用户洞察 / 需求优先级 / MVP 克制
A2 领域知识产品化构建 59 项构件词表 + 5 类加权证据推理作为 AI 的约束层，每条候选风格可追溯到具体构件及其得分；设定「模型只识别构件、风格由研究者解释性归并」的能力边界；4 类争议风格「仅展示不打分」；12 项用户扩充词标「未标定·需专家复核」，禁止直接进论文可解释 AI / 模型能力边界 / 专业场景敬畏
A3 模型效果评测与优化（核心亮点）接入本机 Ollama qwen3-vl:4b 做构件草稿预标注；针对「100% 输出 0 框」设计 A/B/C/I/K 五组对照实验（原配置 44.6s / 扩 num_ctx 275.6s / format:json 69.1s / 仅 id 词表 41.5s / think:false 50.6s，均为 0 框），逐项排除参数与格式假设，定位根因为「47 行长词表触发 thinking 死循环 + 解析器只认 JSON」；重构 986 字符紧凑词表 + 四层容错解析 + 超时熔断，实测 13–30 秒稳定出 3–5 个合法框；基于同图波动（3/4/4 框）、bbox 为模型假设坐标、conf 恒 0.8 等证据，判定该模型能力边界为「草稿生成器」而非判定者，并据此规划多模型横向评测模型评测 / 根因归因 / Prompt 与上下文工程 / 技术选型判断
A4 可靠性与数据闭环发现同图三次结果波动（3/4/4 框）、坐标不可靠 → 设计 human-in-the-loop 草稿隔离：橙色虚线草稿，未复核不进 infer() 证据分、不进 YOLO/CSV 正式导出；打通 labelme 双向 JSON 互通并携带 draft/reviewed 状态，修掉 flags 必须为 dict[str,bool] 的兼容坑；8 份试点 141 框 / 23 种非标标签 100% 归一化导入并逐条给出映射报告；设计「人工复核→沉淀标注→构件图谱→训练自动识别」数据飞轮human-in-the-loop / 数据闭环 / 质量门禁
A5 工程与合规针对 Origin:null 被 Ollama 403，设计 4 端点候选 + 逐端点失败诊断 + 父窗口来源直连，实现零安装、零常驻服务；全链路 localhost、照片不出本机；建立 node --check + headless 8 视图 0 报错 + 内置自检的回归基线；系统预留 MODEL_ADAPTER 适配层（impl(imgEl,opts) 契约），约定换模型只改一处、界面不用动，为后续多模型评测留出替换点隐私合规 / 可扩展架构 / 交付质量

· AI 方案：构建 59 项构件词表 + 5 类加权证据推理作为模型约束层，使每条候选风格可追溯至具体构件及得分；

· 模型评测与选型：针对本地 4B 多模态模型构件识别不足，设计 5 组对照实验逐项排除参数与输出格式假设，
  定位「长词表触发 thinking 死循环 + 解析器只认 JSON」根因，重构紧凑词表、四层容错解析与超时熔断，
  实测从 100% 空输出恢复为 13–30 秒稳定输出 3–5 个候选框；基于同图结果波动与坐标不可靠，
  判定其能力边界为「草稿生成器」而非判定者，并建立评测基线以支撑后续多模型横向选型。
· 可靠性设计：针对模型输出不稳定性，设计 human-in-the-loop 草稿隔离机制——未经人工复核不进入证据分与正式导出；
  打通 labelme 双向 JSON 互通并携带复核状态，8 份试点标注 141 个框、23 种非标标签 100% 归一化导入，
  形成「人工复核→沉淀标注→反哺模型」数据闭环。
· 工程与合规：设计多端点连接诊断与父窗口直连方案绕开浏览器跨域限制，实现零安装、零常驻服务；
  全链路本地运行、照片不出本机，满足文保/规划场景数据合规要求。
· 交付结果：产出 8 视图纯前端工作台，覆盖 980 张照片清洗、618 张人工筛选、50 张自动透视校正与 17 条文献溯源；
  通过 node --check、headless 8 视图 0 报错、内置自检 20/20 的回归基线。

⚠️ 一处必须说准的细节：MODEL_ADAPTER 目前是风格推理层的适配器（{mode:'rule', impl:null}，接口契约为 impl(imgEl,opts)），不是 VLM 调用层的 Provider 抽象。所以上面写的是「设计可插拔模型适配层（统一推理契约），使后续模型替换不改动界面与业务逻辑」——这是真的；不要写成「已实现 VLM Provider 热切换 / 多模型一键切换」，面试官一问代码就穿。若你后续真在 VLM 调用层做了统一封装，再把这句升级为「实现多模型 Provider 抽象」。

面试官最可能追问的数字与判断，你的真实底牌：

追问怎么答（都有实测记录支撑）

【新】「为什么想换模型？换更大的就一定更好吗？」不一定，所以我先做错误归因。当前识别不到位至少有四类可能：① 模型参数量小；② 59 个细粒度构件（如 broken_pediment、pintu_pagar）超出通用 VLM 的语义覆盖；③ prompt 词表/上下文设计（已实测长词表会触发死循环，换模型后仍需重调）；④ 缺乏 few-shot 示例与领域参考。已有实测与文献都指出零样本方法在专业建筑类别上假阳性高、不可复现，所以「换模型」只是候选解之一，知识增强（构件图谱 / RAG）与数据飞轮可能才是根本解。
【新】「你怎么判断哪个模型更好？」不靠主观感觉，用统一评测集 + 四维指标：构件召回/误报（对照人工金标准）、坐标稳定性（同图重跑一致性）、单张延迟、以及是否支持本地部署（合规硬约束）。每个模型跑同一批图、同一套 prompt 模板，输出决策矩阵再选型。详见 §7。
【新】「如果换了模型还是不行呢？」那反而是最有价值的结论：说明瓶颈是领域语义鸿沟而非算力，产品方向应从「换模型」转向「给模型补知识」——构件图谱 few-shot → RAG 检索增强 → 用人工复核沉淀的数据训专用检测器，也就是我设计的数据飞轮。这条推理链本身就是我做技术选型的依据。

7. 【v0.2 新增】模型评测与选型专题：把「试几个模型」写成 PM 能力

7.1 先纠正一个判断：换模型 ≠ 解决构件识别问题

你现在的观察是「这个模型明显对构件识别不到位」，这没错。但直接横向试几个模型，很容易做成一份没有结论的对比（面试官最怕听到「我试了几个，感觉 XX 比较好」）。正确的次序是：

① 错误归因（为什么识别不到位） → ② 建统一评测集与指标 → ③ 横向跑模型
   → ④ 输出决策矩阵 → ⑤ 得出选型结论 → ⑥ 反哺产品架构

四类可能根因，只有第 ① 类能靠换模型解决：

根因换模型是否有效更对症的解法
① 模型参数量小 / 视觉能力弱✅ 有效换更大或更强的 VLM
② 细粒度构件语义缺失（通用 VLM 没见过专业类目）⚠️ 有限构件图谱 few-shot / RAG 检索增强 / 领域微调
③ Prompt 与上下文设计（已实测 47 行长词表触发死循环）❌ 换模型反而要重调紧凑词表、结构化输出、容错解析
④ 图像质量（斜拍、遮挡、白边）❌ 无关四点校正 + 质量门禁（你已有 50 张「待定」机制）

这正好和已确认的产品路线闭环：§1.7.1 里构件图谱的三种用法（参考面板 / RAG / 训练集）就是为 ② 准备的。所以「换模型」不是另起炉灶，而是验证「知识增强」是否必要的对照组。

7.2 评测方案骨架（可直接执行，也是作品集第 6 页的素材）

评测集：从 50 张已校正图里固定抽 10–15 张（覆盖山花 / 柱式 / 窗 / 入口 / 装饰线脚，含 2–3 张遮挡或斜拍难例），由你人工标出构件金标准。注意：换模型时 prompt 词表必须保持 47 项紧凑格式，否则会重新触发 §3.8 的 thinking 死循环——这条约束本身就是评测要控制的变量。

指标（四维，全部可量化）：

维度指标为什么重要
效果构件召回率 / 误报率（对照金标准）、草稿采纳率（人工不改动的框占比）直接决定「省不省人工」
稳定性同图重跑 3 次的框数波动、IoU 一致性专业场景要可复现，波动大就不能当判定者
效率单张推理延迟、0 框失败率无 GPU 环境下决定可不可用
合规/成本是否支持本地部署、显存/内存占用、是否需上传云端文保/规划场景是一票否决项

候选模型分三组（保持对照意义，而不是随便挑几个）：

  • 本地小模型组：qwen3-vl:4b（基线）、更大参数的本地 VLM（验证「参数量」假设）
  • 本地结构优化组：同一模型 + 构件图谱 few-shot / 精简词表（验证「知识增强」假设）
  • 云端强模型组（仅用于对照研究，注意照片出域问题）：若必须用云端，只用公开/脱敏样例图跑，并在作品集里说明「未用于真实田野数据」——这反而能体现你的合规意识

决策矩阵：每个模型 × 四维指标打一行，最后写一页结论：「在 指标上， 模型最优；但受 约束（合规/延迟），最终选型为 ；若 __ 则转向知识增强路线」。这一页就是 PM 的选型产出，比代码值钱。

7.4 如果换了模型还是不行：这是最值钱的结论，别藏

若实测发现「更大模型对细粒度构件仍不可靠」，不要当成项目失败，直接写成技术选型判断：

「横向评测表明单纯增大模型参数量无法弥合专业构件语义鸿沟，据此将产品重心从『换模型』转向『给模型补知识』——以构件图谱提供 few-shot 参考、以人工复核沉淀训练数据，形成数据飞轮。」

这句话在面试官眼里是高级判断：你没有被「更大模型 = 更好」的惯性带跑，而是用实验否证了一个假设，并据此调整产品路线。这比「我换了个更强的模型，效果变好了」有分量得多。

7.5 一句提醒

「尝试几种大模型」是你的下一步计划，不是已完成成果。所以这一轮我没有把它写进简历正文，只写了你为它已经做好的准备（对照实验、能力边界判断、可插拔适配层、评测基线）——这些是真实发生、且恰恰证明你具备选型能力的东西。等评测真跑完，再用成品 C 替换，简历就完成了一次由数据驱动的迭代。这个过程本身，就是你面试时最该讲的「产品迭代」故事。
